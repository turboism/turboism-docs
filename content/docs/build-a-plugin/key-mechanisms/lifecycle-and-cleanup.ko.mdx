이 페이지는 [단계 2](/docs/build-a-plugin/first-plugin/hello-action)에서 사용한 수명 주기 모델을 설명합니다. 여러 진입점, 오래 유지되는 리소스, 핫 리로드처럼 액션 하나 이상을 추가할 때 읽어 보세요.

## 네 가지 메서드

```java
public interface TurboismPlugin {
    default void init(PluginContext context) throws Exception {}
    default void enable() throws Exception {}
    default void disable() throws Exception {}
    default void shutdown() throws Exception {}
}
```

네 가지 모두 선택적 기본 구현입니다. 필요한 것만 구현하세요.

| 메서드 | 목적 | 일반적인 내용 |
| --- | --- | --- |
| `init` | 권한 범위가 적용된 `PluginContext`를 받고 플러그인 비공개 상태를 구성합니다. | 컨텍스트를 보관하고 구성 스키마를 등록합니다. |
| `enable` | 활성 동작을 시작합니다. | 액션, 메뉴, UI, 이벤트 구독, 작업을 등록합니다. |
| `disable` | Runtime이 플러그인 스코프를 닫기 전에 활성 동작을 중지합니다. | 직접 시작한 작업을 중지합니다. |
| `shutdown` | 스코프가 소유하지 않는 플러그인 비공개 리소스를 해제합니다. | 참조를 버리고 비공개 파일을 닫습니다. |

메서드가 특정 스레드에서 실행된다고, 또는 두 호출이 같은 스레드에서 실행된다고 가정하지 마세요. [스레드와 작업](/docs/build-a-plugin/key-mechanisms/threads-and-tasks)을 참고하세요.

## 시작은 원자적입니다

하나의 JAR는 여러 진입점을 선언할 수 있습니다. 이들은 하나의 플러그인 정체성, 하나의 디스크립터, 하나의 ClassLoader, 하나의 `PluginContext`, 하나의 `DisposableScope`, 하나의 권한 집합, 하나의 구성 및 저장소 네임스페이스를 공유합니다.

```text
construct / init / enable:  manifest order
disable / shutdown:         reverse manifest order
```

어떤 진입점이든 생성, `init` 또는 `enable` 중에 실패하면 Runtime은 **JAR 전체**를 롤백합니다. `init`이 실패하면 `enable`은 실행되지 않습니다. `init`은 빠르고 부수 효과가 적도록 설계하고, 눈에 보이는 동작은 `enable`에 두세요.

실패하면 모든 것이 롤백되므로, "시작할 수 없다"는 신호로는 예외가 올바른 방법입니다. 예외를 삼키고 반쯤 초기화된 채로 계속 진행하는 것은 그렇지 않습니다.

## 등록과 disposable 스코프

거의 모든 레지스트리 호출은 `AutoCloseable` 핸들인 `Registration`을 반환합니다. 이를 닫으면 등록한 것이 철회됩니다.

```java
Registration action = context.actions().register("example.refresh", example);
context.disposableScope().register(action);
```

스코프는 플러그인이 비활성화될 때 전달받은 모든 것을 **역순으로** 닫습니다. 이것이 가장 중요한 정리 규칙입니다:

> 현재 메서드보다 오래 살아남을 수 있는 모든 반환된 등록이나 핸들은 명시적으로 닫거나 `context.disposableScope()`에 등록해야 합니다.

등록 대상은 액션, 메뉴 및 도구 모음 기여, 설정 기여, 이벤트 구독, 작업 핸들, 그 밖에 SDK가 닫을 수 있는 형태로 돌려주는 모든 것입니다. 이를 등록해 두어야 Runtime이 플러그인의 ClassLoader를 안전하게 해제할 수 있습니다.

### 비활성화한 뒤 다시 활성화하기

비활성화하면 등록이 철회됩니다. 다시 활성화할 때는 등록을 다시 해야 하므로, 등록은 `init()`이 아니라 `enable()`에 두세요. 그래서 Parameter Peek의 `enable()`은 매번 액션과 메뉴 항목을 생성하고, `init()`은 컨텍스트를 보관하고 구성 스키마를 등록하기만 합니다.

또한 다시 활성화할 때 유지되면 안 되는 상태는 초기화하세요. Parameter Peek가 `enable()`에서 `observedEdits.set(0)`을 호출하는 이유입니다.

### 스코프가 알지 못하는 것 정리하기

스코프는 전달받은 핸들만 닫습니다. 다른 방법으로 시작한 것은 직접 중지해야 합니다. 무거운 오브젝트를 담은 필드, 직접 연 연결, 오래 유지되는 캐시가 그 예입니다. `disable()` 또는 `shutdown()`에서 처리하세요. 스레드, 실행기, 타이머를 직접 만들지 마세요. 핸들을 등록할 수 있는 관리형 [작업 스케줄러](/docs/build-a-plugin/key-mechanisms/threads-and-tasks)를 사용하세요.

## 핫 리로드

디스크립터의 `lifecycle.hotReload: true`는 Cubism을 재시작하지 않고도 플러그인을 메모리에서 활성화, 비활성화, 업데이트할 수 있음을 선언합니다. 다음 조건을 모두 만족할 때만 정직한 선언입니다:

- 플러그인이 표준 SDK 서비스만 사용합니다;
- 닫을 수 있는 모든 것이 disposable 스코프 또는 `disable()`을 통해 해제됩니다;
- 플러그인이 **바이트코드 변환기나 네이티브 훅을 등록하지 않습니다**.

호스트 바이트코드를 변환하는 플러그인은 Runtime이 다음 Cubism 시작 시 변경 사항을 적용하도록 `false`를 선언해야 합니다. `true`를 선언하는 것은 비활성화하면 정말로 아무것도 남지 않는다는 약속입니다. 이 약속은 [단계 6](/docs/build-a-plugin/first-plugin/test-and-ship)의 두 번째 단위 테스트로 검증하세요.

## 흔한 실수

| 실수 | 영향 | 해결 방법 |
| --- | --- | --- |
| `init()`에서 액션 등록 | 비활성화 시 철회되며, 다시 활성화할 때 `init`이 반드시 다시 실행되는 것은 아닙니다. | `enable()`에서 등록하세요. |
| `disposableScope().register(...)`를 잊음 | 비활성화 후에도 등록이 남아 플러그인의 ClassLoader를 붙잡아 둘 수 있습니다. | 모든 핸들을 등록하세요. |
| `enable()`에서 예외를 삼킴 | 플러그인이 활성화된 것처럼 보이지만 기능의 절반이 빠져 있습니다. | Runtime이 롤백할 수 있도록 예외를 전파하세요. |
| `Parameter` 등 모델 오브젝트를 필드에 보관 | 문서 전환 후 안전하게 실패(fail closed)합니다. | 매번 `context.cubism()`에서 다시 해석하세요. |
| 직접 스레드나 타이머 시작 | Runtime의 통제 밖에 있으며 비활성화 후에도 살아남습니다. | `context.tasks()`를 사용하고 핸들을 등록하세요. |
