이제 플러그인을 실제로 실행합니다. JAR를 Turboism에 설치하고, Cubism을 재시작하고, 명령을 실행한 뒤 로그에서 출력을 찾습니다.

## 1. JAR 확인

```bash
./gradlew build
```

아카이브 목록을 출력하여 Runtime이 보게 될 내용을 확인합니다:

```bash
unzip -l build/libs/parameterpeek-turboism-plugin-0.1.0.jar
```

작성한 클래스, `META-INF/turboism/plugin.json`, `META-INF/turboism/cubism-versions.json`, `i18n` 카탈로그가 보여야 합니다. `dev/turboism/sdk/` 클래스는 **보이지 않아야** 합니다. 생성된 `ParameterPeekPlugin__TurboismSubscriberCatalog.class`와 `META-INF/services/...GeneratedSubscriberCatalog` 항목은 어노테이션 프로세서가 만든 것이며 정상입니다.

## 2. JAR 설치

1. 중요한 Cubism Editor 세션은 닫거나 작업을 저장하세요. 설치는 재시작 후에 적용됩니다.
2. Turboism 런처로 Cubism Editor를 시작하고 **Turboism** 메뉴를 엽니다.
3. **플러그인 관리…**, **JAR에서 설치…** 항목을 차례로 선택하고 `parameterpeek-turboism-plugin-0.1.0.jar`를 고릅니다.
4. JAR를 **로컬/미검증 소스**로 표시하는 대화 상자를 확인합니다. Turboism은 직접 빌드한 JAR를 보증할 수 없으며, 이 대화 상자가 그 사실을 알려 줍니다.
5. 작업이 **보류 중**(pending)으로 표시되는지 확인합니다.
6. Cubism을 완전히 종료한 뒤 **같은** Turboism home으로 다시 시작합니다.
7. **Turboism → 플러그인 관리…** 항목을 다시 열어 **Parameter Peek**가 목록에 있고 사용 설정되어 있는지 확인합니다. 두 번 클릭하면 선언한 SDK API 범위와 Cubism 버전을 포함한 세부 정보를 볼 수 있습니다.

설치는 즉시 적용되지 않고 스테이징됩니다. Turboism은 파일을 신뢰할 수 없는 입력으로 취급하여 검증하고, 보류 상태로 스냅샷한 뒤, 다음 시작 시 적용합니다. 교체와 제거를 포함한 전체 흐름은 [플러그인 관리](/docs/use/plugin-management)를 참고하세요.

### 핵심 메커니즘: Runtime이 JAR에서 확인하는 것

JAR를 스테이징하기 전과 시작 시에 Runtime은 다음을 검증합니다:

- JAR가 크기, 항목 수, 압축 해제 크기, 압축 비율 제한 내의 일반 파일입니다;
- `META-INF/turboism/plugin.json`이 정확히 하나 있고, 디스크립터의 ID, 버전, API 범위가 일관됩니다;
- 선언된 진입점이 존재하고, public이며, `TurboismPlugin`을 구현하고, public 매개변수 없는 생성자를 가집니다;
- 선언된 모든 리소스 루트와 i18n 카탈로그가 존재하며, 선언되지 않은 일반 리소스는 없습니다;
- 복사된 SDK, Runtime, 테스트 또는 Live2D 클래스, 네이티브 바이너리나 설치 프로그램 페이로드, 중첩 JAR가 없습니다.

그래서 항상 Gradle 빌드가 생성한 JAR를 배포해야 합니다. 임의의 ZIP 이름을 바꾸는 방식은 통하지 않습니다. 전체 목록은 [플러그인 매니페스트 및 패키징](/docs/build-a-plugin/manifest#엄격한-jar-검증)에 있습니다.

## 3. 명령 실행

1. Editor에서 아무 모델 문서나 엽니다.
2. **Tools → Parameter Peek** 아래에서 **Parameter Peek: Report**를 찾습니다. 이 경로는 등록한 `parameterpeek.menu` 텍스트에서 가져옵니다.
3. 실행합니다. `parameterpeek.hello`의 인사 메시지가 상태 표시줄에 나타납니다.

보이지 않으면 [플러그인이 로드되지 않을 때](/docs/build-a-plugin/key-mechanisms/load-failures)를 차근차근 따라가 보세요.

## 4. 로그 줄 찾기

플러그인의 `logger()`는 Turboism 자체 로그에 기록하며, 각 줄에 플러그인 ID가 붙습니다. **Turboism → 로그…** 항목을 선택하여 로그 디렉터리를 열고, 현재 세션 로그를 열어 `com.example.parameterpeek`를 검색하세요. 다음이 보여야 합니다:

```text
Parameter Peek initialized
Parameter Peek enabled
Hello from Parameter Peek!
```

순서가 중요합니다. `initialized`가 먼저, 그다음 `enabled`, 그리고 명령을 실행할 때마다 작성한 메시지가 나옵니다.

진단에는 `System.out`이나 직접 만든 로그 파일 대신 `context.logger()`를 사용하세요. 로거는 플러그인 범위로 동작하며 출력이 호스트 로그와 함께 수집되므로, 사용자나 유지 관리자가 가장 먼저 확인하는 곳에 남습니다.

## 5. 편집-빌드-설치 루프

일반적인 개발 루프는 다음과 같습니다:

1. 코드를 편집합니다.
2. `./gradlew build`.
3. 새 JAR로 **플러그인 관리… → JAR에서 설치…** 항목을 실행합니다. 같은 플러그인 ID의 JAR는 교체를 스테이징합니다.
4. Cubism을 재시작하고 다시 테스트합니다.

플러그인을 교체하기 전에 중요한 플러그인 데이터를 백업하세요. 적용에 실패하면 이전 플러그인 파일은 복원되지만, 사용자 자신의 데이터는 사용자 책임입니다.

더 빠르게 로컬에서 반복하려면 신뢰하는 JAR를 `<turboism.home>/plugins/`의 루트(하위 디렉터리 아님)에 직접 복사하고 재시작할 수도 있습니다. 이 방법은 위의 관리형 사전 점검을 건너뛰므로 직접 빌드한 파일에만 사용하고, 사용자가 보게 될 거부 결과를 정확히 확인하려면 **JAR에서 설치…** 항목을 사용하세요. 같은 플러그인 ID의 이전 JAR는 먼저 제거하세요. ID가 중복되면 `DUPLICATE_PLUGIN_ID`로 실패합니다.

디스크립터의 `lifecycle.hotReload: true`는 Cubism을 재시작하지 않고도 플러그인을 메모리에서 활성화, 비활성화, 업데이트할 수 있음을 선언합니다. 특정 변경을 Runtime이 메모리에서 적용할지 및 언제 적용할지는 업데이트 경로(예: 플러그인 마켓의 백그라운드 업데이트)가 결정합니다. 로컬 루프에서는 재시작을 전제로 계획하세요.

## 체크포인트

- **Parameter Peek**가 **Turboism → 플러그인 관리…** 창에 표시되고 사용 설정되어 있습니다.
- **Tools → Parameter Peek**가 실행되고 인사 메시지가 상태 표시줄에 나타납니다.
- 로그에 플러그인 ID가 붙은 `initialized`, `enabled`, 그리고 작성한 메시지가 표시됩니다.
