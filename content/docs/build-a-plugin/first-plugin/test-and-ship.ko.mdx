플러그인이 동작합니다. 이 마지막 단계에서는 플러그인을 신뢰할 수 있게 만듭니다. Cubism이 필요 없는 계약은 테스트로 검증하고, 나머지는 실제 호스트에서 직접 확인하고, 메타데이터를 정리한 뒤 JAR를 다른 사람에게 전달합니다.

## 1. 호스트 없이 테스트할 것

단위 테스트는 플러그인이 등록해야 할 것을 등록하고 다시 제거하는지 증명할 수 있습니다. Cubism이 어떻게 동작하는지는 증명할 수 없습니다. 전자는 테스트로, 후자는 실제 호스트 실행으로 다루세요.

호스트 없이 테스트할 가치가 있는 것:

- `enable()`이 수행한 등록과, 스코프가 닫힐 때의 제거;
- 선택적 서비스를 사용할 수 없을 때의 동작(여기서는 기본 컨텍스트의 `config()`와 `localization()`);
- 파싱이나 포맷팅처럼 따로 추출한 순수 로직.

`build.gradle.kts`에 JUnit을 추가합니다. SDK는 `compileOnly`이므로 테스트 클래스패스에 포함되지 않습니다. 테스트에 명시적으로 추가하세요:

```kotlin title="build.gradle.kts"
repositories {
    mavenLocal()
    mavenCentral()
}

dependencies {
    // ... existing compileOnly and annotationProcessor entries
    testImplementation(sdkJars)
    testImplementation(platform("org.junit:junit-bom:5.11.3"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test {
    useJUnitPlatform()
}
```

## 2. 가짜 `PluginContext` 작성

`PluginContext`는 인터페이스이므로 테스트에서 직접 구현해 제공할 수 있습니다. 플러그인이 사용하는 것만 구현하세요. 선택적 서비스는 이미 비활성 상태의 "사용 불가" 구현을 기본값으로 가지며, 이 테스트에서 `config()`가 바로 그래야 합니다.

```java title="src/test/java/com/example/parameterpeek/ParameterPeekPluginTest.java"
package com.example.parameterpeek;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import dev.turboism.sdk.action.ActionRegistry;
import dev.turboism.sdk.cubism.CubismFacade;
import dev.turboism.sdk.diagnostics.DiagnosticReport;
import dev.turboism.sdk.event.EventBus;
import dev.turboism.sdk.i18n.PluginLocalization;
import dev.turboism.sdk.menu.MenuRegistry;
import dev.turboism.sdk.permission.PluginPermission;
import dev.turboism.sdk.plugin.DisposableScope;
import dev.turboism.sdk.plugin.PluginContext;
import dev.turboism.sdk.plugin.PluginDescriptor;
import dev.turboism.sdk.plugin.PluginLogger;
import dev.turboism.sdk.plugin.PluginPaths;
import dev.turboism.sdk.ui.UiScheduler;
import java.util.ArrayList;
import java.util.List;
import java.util.Locale;
import org.junit.jupiter.api.Test;

class ParameterPeekPluginTest {

    @Test
    void enableRegistersOneActionAndOneMenuEntry() throws Exception {
        final FakeContext context = new FakeContext();
        final ParameterPeekPlugin plugin = new ParameterPeekPlugin();

        plugin.init(context);
        plugin.enable();

        assertEquals(List.of("parameterpeek.report"), context.actionIds);
        assertEquals(1, context.menuCount);
    }

    @Test
    void closingTheScopeWithdrawsEveryRegistration() throws Exception {
        final FakeContext context = new FakeContext();
        final ParameterPeekPlugin plugin = new ParameterPeekPlugin();
        plugin.init(context);
        plugin.enable();

        plugin.disable();
        context.scope.close();

        assertTrue(context.actionIds.isEmpty());
        assertEquals(0, context.menuCount);
    }

    /** Implements only what the plugin touches; everything else is deliberately inert. */
    private static final class FakeContext implements PluginContext {
        final DisposableScope scope = new DisposableScope();
        final List<String> actionIds = new ArrayList<>();
        int menuCount;

        @Override public ActionRegistry actions() {
            return (id, action) -> {
                actionIds.add(id);
                return () -> actionIds.remove(id);
            };
        }

        @Override public MenuRegistry menus() {
            return contribution -> {
                menuCount++;
                return () -> menuCount--;
            };
        }

        @Override public PluginLocalization localization() { return new KeyEchoLocalization(); }
        @Override public DisposableScope disposableScope() { return scope; }
        @Override public PluginLogger logger() { return new SilentLogger(); }
        @Override public List<PluginPermission> permissions() { return List.of(); }
        @Override public PluginDescriptor descriptor() { return null; }
        @Override public PluginPaths paths() { return null; }
        @Override public CubismFacade cubism() { return null; }
        @Override public EventBus eventBus() { return null; }
        @Override public UiScheduler uiScheduler() { return null; }
        @Override public DiagnosticReport diagnostics() { return null; }
    }

    /** Returns each message key unchanged, so tests do not depend on catalog wording. */
    private static final class KeyEchoLocalization implements PluginLocalization {
        @Override public Locale locale() { return Locale.ENGLISH; }
        @Override public String text(final String key) { return key; }
        @Override public String format(final String key, final Object... arguments) { return key; }
        @Override public boolean contains(final String key) { return true; }
    }

    private static final class SilentLogger implements PluginLogger {
        @Override public void debug(final String message) {}
        @Override public void info(final String message) {}
        @Override public void warn(final String message) {}
        @Override public void error(final String message) {}
        @Override public void error(final String message, final Throwable throwable) {}
    }
}
```

실행합니다:

```bash
./gradlew test
```

이 테스트에서 이해할 가치가 있는 두 가지:

- 가짜는 `config()`를 제공하지 않습니다. 기본값은 사용 불가 센티널이므로 `init`은 5단계에서 작성한 `isAvailable()` 분기를 탑니다. `init`이 `registerUserEditableSchema`를 가드 없이 호출했다면 이 테스트는 `UnsupportedOperationException`으로 실패했을 것입니다. 여기서는 몇 밀리초 만에 찾는 버그이며, 그렇지 않으면 혼란스러운 사용자 보고로 발견하게 됩니다.
- 두 번째 테스트가 수명 주기 버그에서 중요한 테스트입니다. 액션을 `disposableScope()`에 넣는 것을 잊었다면 `actionIds`가 비어 있지 않을 것입니다. 이 패턴을 추가하는 모든 등록으로 확장하세요.

검증되는 것은 플러그인 자체의 로직뿐입니다. 단위 테스트가 통과해도 플러그인이 어떤 Cubism 버전에서 동작한다는 것을 보여 주지는 않습니다.

## 3. 실제 호스트에서 테스트

컴파일과 가짜 객체로는 Editor가 어떻게 동작하는지 알 수 없으며, 사용자가 플러그인을 실행하는 곳은 Editor입니다. 빌드를 공유하기 전에 연습용 모델로 Editor에 설치하고 이 체크리스트를 따라가 보세요:

- [ ] 설치되고, 재시작되고, **플러그인 관리…** 창에서 사용 설정됨으로 표시됩니다.
- [ ] **모델이 열려 있지 않아도** 명령이 나타나고 오류 없이 실행됩니다.
- [ ] 모델을 연 상태와 파라미터를 편집한 후에 올바른 횟수를 보고합니다.
- [ ] 설정이 표시되고, 적용되고, 재시작 후에도 유지됩니다.
- [ ] 플러그인을 비활성화하면 메뉴 항목이 제거되고, 다시 활성화하면 복원됩니다.
- [ ] 제거 후 재시작하면 사용자가 유지하기로 선택한 데이터 외에는 아무것도 남지 않습니다.
- [ ] `cubism-versions.json`에 나열한 각 Cubism 버전을 실제로 실행해 보았습니다. 실행하지 않은 버전은 제거하세요.

사용한 Turboism 버전, Cubism 버전, 절차를 기록하세요. 실행하지 못한 버전이 있다면 동작한다고 주장하지 말고 그 사실을 밝히세요. AI 지원 작업에 같은 기준을 적용하는 방법은 [LLM으로 개발하기](/docs/build-a-plugin/llm-coding-context#개발자-요구-사항)를 참고하세요.

## 4. 메타데이터 마무리

사용자의 관점에서 `plugin.json`을 검토하세요:

| 필드 | 확인 사항 |
| --- | --- |
| `id` | 역도메인 형식이고, 고유하며, 최종본이어야 합니다. 나중에 바꾸면 다른 플러그인이 만들어집니다. |
| `version` | 배포하는 모든 릴리스마다 올리고, 파일 이름이 일치하도록 `build.gradle.kts`의 `version`과 같게 유지하세요. |
| `turboismApi` | 최솟값은 사용하는 모든 SDK 멤버를 제공하는 가장 이른 프레임워크 API여야 합니다. 더 새로운 SDK로 컴파일한다고 해서 그 추가 기능이 더 오래된 Runtime에서 동작하게 되지는 않습니다. `[min,max)`의 상한은 `1.0.0` 미만으로 유지합니다. |
| `description`, `authors`, `license`, `website` | 실제의 최신 값이어야 하며 템플릿의 자리 표시자 값이면 안 됩니다. |
| `permissions` | 각각 실제로 사용되며 검토자가 받아들일 만한 `reason`을 가져야 합니다. 실험하면서 추가한 것은 제거하세요. |
| `category`, `tags` | 맞는 것이 있으면 검토된 카테고리를 사용하세요. 태그는 소문자 kebab-case이며 최대 12개입니다. |
| `environment.requiresCubism` | 여기처럼 실행 중인 Editor가 필요하면 `true`입니다. |
| `lifecycle.hotReload` | [플러그인 매니페스트 및 패키징](/docs/build-a-plugin/manifest#lifecycle-및-핫-리로드)의 조건을 충족하는 경우에만 `true`입니다. |

또한 `cubism-versions.json`(테스트한 버전만, `fullFeatureVersions`는 `supportedVersions`의 부분집합)과, `i18n.locales`에 나열한 모든 로캘에 카탈로그 파일이 있는지 확인하세요.

## 5. JAR 공유

`build/libs/`의 파일이 배포 대상입니다. 설치 프로그램도 래퍼 아카이브도 없습니다. 다른 사람에게 전달하려면:

1. `./gradlew clean build`로 깨끗한 상태에서 빌드합니다.
2. 버전, 테스트한 Turboism 및 Cubism 버전, 요청하는 권한과 그 이유에 대한 짧은 설명과 함께 JAR를 보냅니다.
3. 받는 사람은 **플러그인 관리… → JAR에서 설치…** 항목으로 설치하고, 로컬/미검증 소스 대화 상자를 확인한 뒤 재시작합니다. [플러그인 관리](/docs/use/plugin-management)를 참고하세요.

이것이 로컬 설치임을 분명히 밝히세요. Turboism은 이런 방식으로 설치된 JAR를 검토하거나 인증하지 않습니다.

### 플러그인 디렉터리는 선별형입니다

[플러그인 디렉터리](https://turboism.dev/plugins)는 Turboism 팀이 관리하는 선별형 카탈로그이며 셀프서비스 마켓플레이스가 아닙니다. 서드파티 목록은 아직 공개되지 않았으며, 빌드할 수 있다고 해서 디렉터리에 등재될 자격이 생기는 것은 아닙니다. 배포를 염두에 두고 설계하고, 후보 플러그인을 논의하려면 [Turboism GitHub 조직](https://github.com/turboism)을 이용하세요. 현재 상태는 [기여](/docs/build-a-plugin/contributing)를 참고하세요.

## 다음으로 할 일

이제 전체 루프(생성, 빌드, 설치, 관찰, 반응, 영속화, 테스트, 배포)를 갖추었습니다. 더 깊이 들어가려면:

- [핵심 메커니즘](/docs/build-a-plugin/key-mechanisms/lifecycle-and-cleanup) 페이지를 순서대로 읽으세요. 2~5단계에서 이해하지 못한 채 사용한 것을 설명합니다.
- 설계 체크리스트는 [플러그인 설계](/docs/build-a-plugin/designing-plugins)를 공부하세요. 특히 모델을 수정하기 전에 쓰기 안전 규칙을 확인하세요.
- [퍼스트 파티 플러그인](/docs/use/first-party-plugins)에서 퍼스트 파티 플러그인을 살펴보고, 아직 사용하지 않은 서비스(도구 모음, 컨텍스트 메뉴, 작업, 저장소, 사용자 파일)는 [SDK API 가이드](/docs/reference/sdk-api)를 참고하세요.
- Parameter Peek를 확장해 보세요. 같은 액션에 도구 모음 버튼을 추가하거나, 변경 횟수를 `storage()`에 영속화하거나, `messages_zh_Hans.properties`와 두 번째 로캘을 추가해 보세요.
